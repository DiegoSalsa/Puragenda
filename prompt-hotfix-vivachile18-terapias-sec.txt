Necesito un HOTFIX URGENTE en Puragenda para corregir la aplicación del código de descuento `VIVACHILE18`, correspondiente a un 18% de descuento.

## Contexto del problema

Tenemos un negocio llamado **Terapias SEC**.

Este negocio anteriormente tuvo beneficios/promociones de meses gratuitos:

* inicialmente tuvo pruebas/meses gratis;
* posteriormente quedó con 2 meses gratis.

Ahora Terapias SEC quiere comenzar a pagar normalmente utilizando el código:

`VIVACHILE18`

El código otorga **18% de descuento**, pero actualmente, al intentar utilizarlo, el sistema indica que:

> el código no sirve para su cuenta

Necesitamos solucionar esto inmediatamente para que Terapias SEC pueda realizar el pago.

## Objetivo

Identifica exactamente por qué el sistema está rechazando `VIVACHILE18` para la cuenta de Terapias SEC y corrige la lógica para que pueda utilizarlo.

NO asumas la causa.

Primero inspecciona:

* modelo/configuración de cupones;
* validaciones de elegibilidad;
* historial de trials/promociones;
* meses gratuitos;
* promociones previamente utilizadas;
* restricciones tipo `first payment`, `new customer`, `trial`, `subscription`, `coupon already used`, etc.;
* endpoints/API involucrados;
* frontend de checkout;
* backend que valida el cupón;
* creación del pago/preferencia en Mercado Pago;
* cualquier regla asociada específicamente a `VIVACHILE18`.

## Regla funcional requerida

**Terapias SEC debe poder utilizar `VIVACHILE18` y pagar con el 18% de descuento aunque anteriormente haya tenido meses gratuitos o trials.**

Los meses gratuitos anteriores NO deben ser considerados como haber utilizado este código ni deberían bloquear este descuento.

También verifica si el problema corresponde a una regla demasiado restrictiva que pueda afectar legítimamente a otros negocios en la misma situación.

Si `VIVACHILE18` fue diseñado para poder utilizarse en el primer pago real de un negocio, entonces un trial o mes gratuito previo NO debe contar como un pago que invalide el cupón.

No hardcodees el nombre `"Terapias SEC"` como solución salvo que descubras que existe una restricción empresarial explícita y documentada que requiera una excepción. Prefiere corregir la regla de elegibilidad de manera coherente con el modelo actual.

## Seguridad

No debes:

* permitir reutilización ilimitada del cupón;
* permitir que una misma cuenta lo utilice nuevamente si ya lo utilizó realmente;
* romper otros códigos promocionales;
* modificar importes de pagos ya existentes;
* alterar suscripciones de otros negocios;
* eliminar controles antifraude;
* hacer refactors grandes.

El hotfix debe ser **mínimo, localizado y seguro**.

## Validaciones obligatorias

Antes de subir el cambio, prueba como mínimo:

1. Terapias SEC + historial de meses gratis + `VIVACHILE18`
   → DEBE aceptar el código.

2. El importe final debe reflejar exactamente un **18% de descuento**.

3. Cuenta que nunca utilizó el cupón
   → debe seguir pudiendo utilizarlo si cumple las reglas actuales.

4. Cuenta que YA utilizó realmente `VIVACHILE18`
   → debe seguir siendo rechazada si el cupón es de un solo uso por cuenta.

5. Código inexistente o vencido
   → debe seguir siendo rechazado.

6. Otros códigos promocionales existentes
   → no deben cambiar su comportamiento.

7. Verifica tanto la validación mostrada en el frontend como la validación definitiva del backend antes de generar el pago.

8. Ejecuta tests/lint/build correspondientes al proyecto.

## Flujo Git

Esto es un hotfix de producción.

1. Actualiza `origin/main`.
2. Crea una rama desde el último `main`, por ejemplo:
   `hotfix/vivachile18-terapias-sec`
3. Implementa únicamente el cambio necesario.
4. Agrega tests de regresión para la causa encontrada.
5. Ejecuta la batería de validaciones disponible.
6. Verifica build de producción.
7. Si TODO está correcto:

   * commit descriptivo;
   * push;
   * merge a `main`;
   * push de `main`;
   * verifica que el deploy de producción quede correcto.
8. Una vez confirmado el merge, elimina la rama hotfix local y remota.

No dejes el arreglo solamente en una rama de testing: necesitamos que quede operativo en producción para que Terapias SEC pueda pagar.

## Verificación final

Después del deploy, revisa nuevamente el flujo real de aplicación de `VIVACHILE18` hasta el punto inmediatamente anterior a ejecutar un cobro real.

NO realices un pago real ni generes cargos no autorizados.

Comprueba que:

`precio normal → código VIVACHILE18 → -18% → total correcto`
